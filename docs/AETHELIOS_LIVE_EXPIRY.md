# Independent Live expiry — implementation candidate, October 12, 2026

## Decision and researched constraints

Use the existing Vercel Functions/Supabase database rather than introducing Workflow, LiveKit or another queue service for one bounded cleanup operation. Reviewed the installed Vercel Workflow/Supabase skills and current official [Vercel Cron management](https://vercel.com/docs/cron-jobs/manage-cron-jobs), [Cron pricing/limits](https://vercel.com/docs/cron-jobs/usage-and-pricing), [Supabase database functions](https://supabase.com/docs/guides/database/functions), and [OpenAI Realtime hangup](https://developers.openai.com/api/reference/resources/realtime/subresources/calls/methods/hangup). Workflow offers durable orchestration, but a leased periodic retry is sufficient for this pilot's existing database-backed calls. No SDK or subscription is added.

Vercel Cron invokes functions independently of the admitting process/browser, but is not an exact two-minute hard stop. Minute scheduling requires Pro/Enterprise; Hobby's daily schedule is unsuitable. Cron does not immediately retry an error, delivery may overlap, and automatic schedules run on production deployments. Successful real scheduling/provider termination must therefore be measured, including lost/delayed invocations. The provider's maximum session lifetime does not establish the pilot's budget. Supabase changelog markdown retrieval failed; no changelog verification or package upgrade is claimed.

## Implemented

- `/api/internal/live-expiry`: disabled by default; requires `AETHELIOS_LIVE_EXPIRY_ENABLED=true` plus a server-only `CRON_SECRET` of at least 32 characters, checked with constant-time comparison. Rejects query parameters, accepts no model/user session IDs or commands, and returns only private/no-store aggregate counts or redacted errors. Authority is the scheduler credential, not browser Auth, membership, user metadata or a user-agent/header assertion.
- A dedicated infrastructure client reuses the existing billing-control pattern and `SUPABASE_SERVICE_ROLE_KEY` configuration. It can call only the two worker RPCs in this module; no personal table reads, transcripts, normal app actions or service-role user path are introduced. The credential itself is broadly privileged, so it must remain server-only; ordinary clients have no execute grant on the worker RPCs.
- Additive migration stores lease tokens/attempts/confirmation in the unexposed `live_private` schema, with RLS and no user/table grants. Atomic `FOR UPDATE SKIP LOCKED` claims at most five attached expired calls, renews a two-minute lease after a worker dies, and prioritizes first attempts over repeated failures. There is no caller-selected owner or session in the claim API.
- Each claimed row must pass strict shape, expiry and existing server HMAC owner/session/call binding before calling the fixed OpenAI hangup endpoint. Redirects are denied; provider timeout is ten seconds and RPCs are bounded to five seconds. The five calls run concurrently. 404/410 are already-absent outcomes; 401/429/5xx/timeouts remain pending. Bad bindings do not stop valid calls in the same batch.
- Only a successful hangup followed by a true lease-token confirmation records private cleanup. Stale/foreign/expired tokens cannot confirm. Existing usage and end reason are preserved; provider final usage is not fabricated. User-writable `ended_at` is deliberately insufficient to skip the worker: an ended attached call is checked once at expiry and private confirmation stops repeated checks. This can add one idempotent hangup request after ordinary End.
- Added normal founder/member/anonymous Auth assertions denying both worker RPCs, plus a rollback-only local Supabase SQL acceptance fixture in the existing integration CI. No real provider request occurs in these tests.

## Acceptance and remaining limits

Local validation: full lint and strict types pass; **81 files / 533 unit/SQL tests pass**. The 13 focused expiry cases include actual migration SQL in PGlite; the historical 28-file migration ledger also passes. The proxy lets this infrastructure route reach its own scheduler authentication without a browser cookie refresh, matching the existing Stripe webhook boundary. Connected build/browser/real-local-Auth/Postgres checks remain required for this exact candidate.

Unit/SQL tests cover scheduler denial/default off, input refusal, HMAC/expiry validation, isolated failures, redaction, false confirmations, worker role ACLs, bounded non-overlapping leases, recovery after lost workers, stale-token rejection and preserved metering. PGlite tests execute the migration but are not real Auth/provider acceptance. The integration job must additionally pass the real local Auth denials and local Postgres lease fixture on this exact source.

Before activation: confirm approved non-production DB binding; apply/review the additive schema there and run security advisors; configure server-only worker authority; invoke the protected preview manually with real expired/active calls; verify hangup while the admitting function/browser is absent, provider failures/retries and retained billing. Confirm minute scheduling is already supported on the current plan before adding the fragment to actual deployment config. Verify schedule delivery and alert on pending/503/overdue jobs before enabling voice. Keep expiry available when ordinary voice admission is disabled so existing calls can drain.

Capacity is five claims per invocation, appropriate only for the bounded pilot until load tests establish batch/rate/cost limits. A minute scan adds scheduling delay beyond the reservation deadline; lease recovery adds up to two minutes plus scheduler delay. A provider failure can extend that further. Key rotation invalidates old bindings and needs a controlled drain/review. A process death between provider call creation and database attach can leave an unknown call ID that this worker cannot discover. No unattached reservation is falsely declared provider-cleaned. These remain explicit hard-budget/activation risks; production admission continues to reject Live. This code alone does not complete hosted expiry acceptance or establish ChatGPT performance.
