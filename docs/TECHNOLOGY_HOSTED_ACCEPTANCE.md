## Research and implementation decision — 2026-10-09

- [Supabase branching](https://supabase.com/docs/guides/deployment/branching) provides independently credentialed, dataless environments. A separate database is necessary to test these migrations without putting customers at risk. Do not enable automatic merge/deployment to main or copy production data.
- [Branching usage/pricing](https://supabase.com/docs/guides/platform/manage-your-usage/branching): default Micro compute starts at $0.01344/hour; storage, disk and egress can add charges. Branches are outside the spend cap and compute credits do not apply. Four hours of base compute is approximately $0.05376, not an all-inclusive guaranteed quote. Obtain the actual organization quote and explicit infrastructure approval before provisioning; no plan upgrade, domain purchase or customer billing change is authorized here.
- [Vercel Deployment Checks](https://vercel.com/docs/deployment-checks) support candidate-bound release gates. App CI and a READY preview alone do not prove hosted database compatibility, provider quality or permission to publish.
- Vercel's installed protected-deployment guidance prefers short-lived OIDC protection access. The runner forwards `x-vercel-trusted-oidc-idp-token` only to the exact accepted app origin, never to Supabase, redirected external origins or a customer site. It does not disable protection or expose a long-lived bypass token.
- Read installed Next.js 16.3.5 route-handler documentation before the metadata route. The route uses existing environment validation and has no mutation or identity authority.

The useful Phase 8 slice closes a verification gap: prior founder acceptance uses the local `/dev` entry; prior hosted account acceptance covers Mission, Studio, private Storage and account boundaries but not the end-to-end website/package UI. Keep normal creation native and reuse Playwright, ordinary Supabase user sessions and existing server routes. No new AI model, queue, execution sandbox or hosting vendor is required for this slice. Do not invent a publish adapter to claim the operational blocker is resolved.

## What the new acceptance does

`npm run test:creation` runs exactly one serial journey with no retries. Before sending login credentials or writing fixtures, it observes `/api/technology/runtime` and checks the deployment's build-bound Git commit, database reference and environment. Production returns 404. Preview returns only those non-secret identifiers and harness status with no-store headers. A hosted harness must be disabled and `/dev` unavailable.

Hosted execution requires a clean committed checkout and a strict, independently verified operator manifest valid for at most 24 hours. It binds commit, tree, exact immutable Vercel preview origin, nonproduction Supabase reference and two known synthetic Auth/person mappings. The manifest is an operator attestation, not a signature or proof that a branch exists: verify the branch and deployment through provider inventories first. Both public and private production database IDs are explicitly refused. Credentials and a publishable key live only in operator environment variables. Administrative keys are rejected. Never point this test at an unknown preview because it happens to build.

The test authenticates both accounts with normal password login and ordinary SDK sessions, checks their verified identity mappings, creates one synthetic Studio reference and one private 1200×800 raster, and saves one owned synthetic website. Through the actual application it imports imagery, saves/reviews the next version, builds the reviewed version, verifies the embedded static HTML and disabled publication manifest, removes the source image, reloads the retained website, approves and downloads the exact ZIP, compares packaged HTML/hash, reloads approval, checks cross-account/anonymous denial of six private resources and revokes approval. No response interception, fake user headers, live model call, customer records or service-role mutation is involved. Routing only continues requests with origin-scoped protection headers.

Private `test-results/public-creation-acceptance.json` records scope, exact candidate, bounded checks, time, cleanup status and `releaseApproved:false`. No email, password, key, session token, image bytes or stack trace is included; traces/screenshots/video are disabled and errors expose only a bounded stage name. It does not claim local CI is hosted acceptance. Runtime or identity failures precede fixture writes. Cleanup targets only run-created Studio IDs/storage keys. Website records have no owner deletion API and are deliberately retained as one bounded synthetic project until the approved disposable environment is deleted. Report that retained ID; never silently use an admin cleanup key. Each run consumes one project slot; no automatic retries or quota bypass.

CI runs this normal-login journey against disposable real local Supabase before the pre-existing founder journeys, uploads its own acceptance receipt, and keeps all existing application, browser, Auth/RLS, catalog and ledger gates. Automated mobile/tablet/desktop checks remain in the existing browser suite; physical-device acceptance is a separate pending gate.
