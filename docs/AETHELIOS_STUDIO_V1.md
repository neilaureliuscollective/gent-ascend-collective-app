# Aethelios Studio V1 — 2026-09-27

## Scope and architecture

A bounded image workspace at `/app/studio` complements Aethelios Chat. A project contains ordered versions with parent and reference links. The user can create multiple projects, enter a prompt, choose fast/precise and square/landscape/portrait, upload one PNG/JPEG/WebP reference (10 MB maximum), generate one image, return later, and refine a saved image by selecting it as the source. Gallery records persist even if OpenAI provider state expires. This is an image creation surface, not autonomous media workflows or a general chat tool registry.

`Studio UI → same-origin Node route → verified Supabase Auth/person/capability → owner-scoped project/reservation → OpenAI Responses image-generation tool → private Supabase Storage → completed version`. Model credentials remain server-only. New files live in a private `aethelios-studio` bucket under the Auth user ID. Authenticated image delivery checks version/reference ownership before downloading; no persistent signed URLs are emitted. User projects and version lineage are application-owned. The server sends the selected original or saved image as a data URI for each edit with `store:false`, so continuity does not depend on `previous_response_id`. Conversation assets and text turn IDs are not repurposed; a future message/project link can use stable version IDs.

Two image models are exposed: `gpt-image-2.5-flare` for fast exploration and `gpt-image-2.5-sunburst` for precise work, both at medium quality. The existing server-side `AURELIUS_AI_MODEL` orchestrates the image tool. One image per request limits cost. An owner-scoped advisory ledger reserves at most 12 requests in a rolling day; retries consume a reservation because the provider might have billed before a failure. A second concurrent pending request is blocked. A pending row older than five minutes is marked failed on the next reservation. Request UUIDs prevent duplicate generations. The UI does not auto-retry a network failure that could have reached the provider.

## Security and limitations

- `ai_studio_projects`, `ai_studio_references`, `ai_studio_versions`, and `ai_studio_usage` have RLS; composite foreign keys bind versions and references to one owner/project. The private Storage bucket uses Auth UID prefix policies. Generation and completion are database functions using the verified JWT, not service-role user access.
- Reference uploads use a same-origin, authenticated prepare/finalize exchange. The browser sends the file directly to private Supabase Storage with a short-lived signed upload token; the server downloads and validates the signature and actual size before attaching it to an owned project. This avoids Vercel's 4.5 MB request limit. Images served through the app use a streamed, owner-checked, no-store response. The user can still interact with their own Storage objects through their authenticated Supabase client; a removed object may leave a broken gallery item. Reference object garbage collection and complete deletion/export flows need a follow-up lifecycle design.
- Project creation is owner-scoped. This initial workspace displays 100 most recent projects and 100 recent versions in a project; it does not yet paginate beyond them. No asset pruning, metadata strip, detailed provider usage reconciliation, cancellation, partial image preview, masks, multi-reference composition, or billing tier pricing is included.
- The generated image is required to be PNG and at most 10 MB. A provider rejection, timeout or storage error records a failed version and returns a redacted error. The initial prompt is retained for retry by copying/reusing it; there is no automatic regeneration after ambiguous network loss.
- Studio does not silently include memory or personal records in an image request. A future opt-in context policy must be reviewed separately. Model output is not promoted to memory or personal facts.

## Research and decisions

Current OpenAI guidance recommends the Responses API for conversational, editable image experiences, with image inputs as data URIs/file IDs and an image-generation tool; Image API is more direct for one-off generation. The tool supports fast/precise GPT Image 2.5 models, size/quality/output format, and forced tool choice. Application-owned saved images are sent for edits to avoid provider-state lock-in. [OpenAI image generation](https://developers.openai.com/api/docs/guides/image-generation), [image tool](https://developers.openai.com/api/docs/guides/tools-image-generation).

Supabase private buckets enforce RLS for authenticated reads/writes; Storage helper functions allow path-based owner policies. Signed **upload** tokens are scoped to a random object path and valid for two hours. The image read proxy avoids distributing signed **download** URLs. [Private bucket](https://supabase.com/docs/guides/storage/buckets/fundamentals), [access control](https://supabase.com/docs/guides/storage/security/access-control), [signed upload](https://supabase.com/docs/reference/javascript/file-buckets-createsigneduploadurl). Next 16 route handlers can use Web Request/Response and a Node runtime; a host must support the configured 300-second route duration. [Next route handlers](https://nextjs.org/docs/app/getting-started/route-handlers), [Vercel payload limits](https://vercel.com/docs/functions/limitations).

## Verification and release gates

Local `npm run check` validates lint, strict types, database/unit tests and production build. PGlite applies the additive migration with a minimal Storage catalog adapter; a new two-account test checks ownership, duplicate reservation, denied cross-person access, and an enduring usage reservation. `npm run db:ledger` checks existing hosted ledger ordering. These are not live Supabase Storage, Auth, or provider tests.

Before hosted activation: apply chat foundation migration, then Studio migration on protected staging; confirm bucket configuration and two-account Auth/Storage isolation, generate and refine with an organization verified for GPT Image models, inspect actual latency/cost and function timeout, verify phone/Fold/desktop interaction, and test network interruption. No production deployment has occurred. If the hosting plan cannot sustain the synchronous generation duration, move generation to a durable job before release; do not leave requests half-persisted.
